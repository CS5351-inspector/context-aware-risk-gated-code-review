# 精读推荐：清单第 6 篇，企业审查流水线的统一接口

## 唯一推荐

**Hyungjin Kim 等，A Unified Code Review Automation for Large-scale Industry with Diverse Development Environments，ICSE-SEIP 2022，2 页。**

- [作者提供的全文](https://coala17.github.io/paper/paper.pdf)
- [论文首页给出的 DOI](https://doi.org/10.1145/3510457.3513062)

这是你提供的 survey 第 6 篇，适合“企业流水线/基建”的兴趣。你现在开发角色为 C 模型可靠性，也可以从中学习如何把一个分析能力放进统一审查系统；选文不需要机械地跟随“项目成员字母”。本次只推荐这一篇精读。

书目信息核对：survey 给的是 IEEE 风格 DOI `10.1109/ICSE-SEIP55303.2022.9793899`；作者公开 PDF 首页引用使用上述 ACM DOI。记录书目时注明版本来源，不擅自断言两个标识中哪一个无效；以你实际阅读版本的首页为准。

## 论文事实摘要

作者介绍三星的 Code Review Bot：用共同接口隔离不同审查平台，用任务 worker 调度分析服务，并采用并行处理；文章讨论可扩展性、规模与性能。它是工业经验短文，不能直接当作 LLM 准确性或本项目 gate 有效性的证据。全文来源：[作者 PDF](https://coala17.github.io/paper/paper.pdf)。

survey 将规模概括为“百万级评审请求”不宜直接引用；论文中日常代码变更量与 review request 数量是不同口径。写报告时每个数值都应回原文核对时间范围、单位和去重方法，本指导不把它们混成一个指标。

## 三轮精读，约 90 分钟

### 第一轮，15 分钟：只建立地图

先读标题、摘要、两节主体标题和结尾。在纸上画“审查事件 → 接入层 → 分析服务 → 结果反馈”。用自己的话写三句话：谁使用系统；异构环境给接入带来什么麻烦；质量目标除了“能找到问题”还有什么。

不熟悉的术语先记录：extensibility（扩展性）、scalability（规模增长下承载能力）、performance（性能）、worker（任务执行单元）、adapter/interface（隔离实现细节的接口）。不要逐词翻译整篇，先找到问题与方案之间的关系。

### 第二轮，40 分钟：逐段标注证据与缺口

第 1 页读挑战时问：多版本控制/审查平台会影响哪些输入与输出？如果只写一个 GitHub 专用 bot，哪些逻辑会难以复用？

第 2 页读设计时问：公共接口能隐藏哪些平台细节？哪些仍需要平台特定处理？调度与分析服务为什么应该分开？如果模型 API 每次响应时间不同，你会把超时放在哪一层？

读结果表格时，只做方法核对：分子分母分别是什么，是否去重，是否包含所有缺陷类别，修复率能否代表召回率。没有人工 ground truth 或对照组时，哪些因果结论无法成立？这组问题是你的批判性阅读任务。

### 第三轮，35 分钟：转成你自己的需求与验收

给本组提 4 条可验证需求；下面是本指导的迁移示例，不是论文原句：

1. FR：每个分析模块通过共同输入/结果对象交接，不在模块内部写 GitHub 评论。验收：替换 mock 和真实适配器时，风险与报告模块接口不变。
2. NFR：一次 PR 的所有模型尝试受总调用次数与 deadline 约束。验收：多文件加失败重试仍不突破额度。
3. NFR：必要分析失败不能呈现为完整通过。验收：一个文件超时、另一个有 high finding 时保留 finding 并返回 PARTIAL。
4. 可观测性：未知 usage 明确显示未知，保留有效参数和 prompt 版本。验收：缺失 usage 的固定响应不会显示为零成本。

FR 是功能需求，即系统做什么；NFR 是非功能需求，即系统应达到的可靠性、性能或可维护性约束。两类都应有可观察的验收条件。

## 精读笔记模板

| 项目 | 用自己的话填写 |
| --- | --- |
| Problem | 哪种真实环境造成了什么困难？ |
| Design | 接口、服务和调度各承担什么职责？ |
| Evidence | 用什么数据与方法支撑结论？ |
| Limits | 哪些信息不足以支持更强的结论？ |
| Transfer | 我借鉴到 C 模块的哪一处？ |
| Acceptance | 用什么失败案例验证我的迁移？ |

最终准备一页笔记、一张自己画的结构图，以及一个实际通过的可靠性测试。答辩时可以说：“我借鉴统一接口与调度分离的工程思想，把模型看作可能失败的分析服务；我的新增贡献是输出来源验证和受预算约束的调用，而非声称复现了论文工业规模或证明了 LLM 更准确。”
