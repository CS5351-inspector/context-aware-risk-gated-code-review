## Ordinary Write walkthrough

1. On the demonstration branch, inspect the required status name and record the active branch rule, allowed bypass actors and the reviewer's Write role. Use separate author and reviewer accounts and a distinct head for each open demo PR. Keep the PR open through the sequence so each transition remains observable.
2. Open a same-repository PR with an added or modified JavaScript or TypeScript file. Add a harmless file under `demo/policy/` to trigger the HIGH risk rule. Verify that the regular Context run completes its publication and stores the analysis artifact for this head while the gate is waiting. The Write reviewer then approves the head. Verify the success status and review-event receipt, including `reusedAnalysis: true` and `newModelCalls: 0`. After the author pushes another change, check that the original approval cannot authorize it.
3. Obtain a fresh approval. Have a user authorized to dismiss it perform the dismissal and record the actor separately. Have the ordinary Write reviewer request changes on a clean head and capture the resulting restriction. Fault-injection tests supply offline evidence for failures that did not occur in a real run; retain their offline label.
4. For each live transition, record the PR URL, full head SHA, reviewer role, review ID/link, Actions URL, report/comment link, actual status and the Write member's merge-box observation. From the run's artifacts obtain `inspector-receipt-<run_id>-<attempt>/inspector-receipt.json`. Record any missing artifact or denied write directly from the job log.

For an optional resource comparison, run the two modes on the same PR, base, head, workflow revision and configuration. Use the receipt's application duration, new model calls, usage, coverage, omissions and failure reason. Identify cache hits; provider usage can be unknown. Use Actions timestamps to report queue and setup separately. [Actions workflow](../.github/workflows/inspector-live.yml) · [Architecture decision](SPRINT2_GATE_ADR.md)

## Reliability regression coverage and publication boundary

Verified on main `0c1a0b6` plus this change: 18 Jest suites / 502 tests, 43 evaluation tests, typecheck, build and Action syntax check passed. The build retains existing external-dependency warnings.

The 14-case [cross-module suite](../test/reliability-lifecycle.test.ts) exercises the actual GitHub adapter, snapshot, B context, C response validation, pure D and guarded publisher with scripted external HTTP/model responses. It covers complete LOW/MEDIUM passing, HIGH approval, old-head rejection, fresh approval, dismissal, qualified change requests, insufficient permissions, timeout/malformed output/missing patch, explicitly marked human takeover, head changes during publication and rejected report/status writes. This is automated fault-injection evidence, separate from the real GitHub observations above.

The production snapshot now fetches patches from immutable merge-base/head comparisons, checks comparison identity, file count and uniqueness, and rejects missing lists or 300-or-more files because the Compare API cap can conceal truncation. [Snapshot regression](../test/snapshot-pinned.test.ts) · [Adapter regressions](../test/review/github.test.ts). Controlled legacy adapters retain their optional compatibility path.

Publication receipts expose `publication.finalGate`, and the Action receipt also records `finalGate`, separately from historical `gateAtReport`. A report-time PASS followed by a same-head dismissal can finish as WAITING/pending; that final recheck must remain visible. A denied write can leave an older status on GitHub: the run/receipt must expose failure rather than claim successful retraction. These tests do not prove atomic merge authorization or all concurrency schedules.

### Configuration and remaining live acceptance

On November 23, the GitHub branch protection API showed strict required `inspector/risk-gate` from GitHub Actions on `sprint2-demo`, with administrator enforcement. The native required-review setting was empty, so Inspector applies its own current-head approval requirement. During the November 21 demonstration, the ordinary Write reviewer observed GitHub's merge box before and after the required status changed.

D independently requires one eligible current-head approval when complete LOW/MEDIUM automatic passing is unavailable. Adding a native approval requirement for every PR would also restrict LOW/MEDIUM auto-pass cases; confirm the intended policy before changing it. D ignores an old-head approval even if GitHub still displays it as APPROVED. This is distinct from GitHub automatically dismissing that review.

The regular live workflow was re-enabled on November 22 for eligible same-repository PRs targeting `sprint2-demo`. The RelayCore paired pilot and the zero-model #16 exercise were separate runs. Automatic review-event reconciliation and analysis-cache reuse, complete live MEDIUM analysis, provider timeout/missing content/human takeover, running-head races and denied publication remain pending live acceptance. The #16 verifier used a different implementation revision from this hardening change. Its recorded reviews and statuses are historical acceptance evidence.
